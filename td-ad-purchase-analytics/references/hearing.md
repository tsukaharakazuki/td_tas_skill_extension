# 初回ヒアリングと読み取り調査

## 1. 目的を先に決める
一度に全項目を質問せず、分かっている情報を埋めてから不足だけ聞く。

最初の質問例
> どの広告・施策で獲得したCookieが、その後どれだけログイン・購入したかを確認します。今回の施策名、獲得期間、購入を追う期間、WebログのDB・テーブル、プロジェクト名を教えてください。購買データがWebログ以外にあるか、広告費も比較するかも分かる範囲でお願いします。

|項目|確認する内容|
|---|---|
|目的|施策別の新規Cookie獲得、ログイン転換、長期購買、再購入、獲得後7/30/90日、購入前7日流入など|
|プロジェクト|既存 `Project/<name>/MEMORY.md` の有無、名前、更新か新規か|
|獲得期間|`report_start` 以上・`report_end` 未満。日付境界のタイムゾーン|
|観測終了|Workflowセッション時刻未満。データ確定遅延・遅延到着・返品反映|
|Webログ|DB・table、保存開始・欠損期間、複数サイト、同意拒否・Cookie期限・削除|
|識別子|`td_client_id`、会員IDの意味・空値、実際にログインしたと判断できるイベント|
|セッション|SDK session ID列・有効率・生成仕様。なければ30分の無活動でセッショナイズ|
|流入|URL・referrer、UTM・広告ID・キャンペーン名、内部ドメイン・決済ドメイン、施策抽出条件|
|購買|web / separate のどちらを正とするか。注文ID、注文日時、会員ID、注文合計金額、通貨|
|GA4 ecommerce|dataLayerの保存先、JSON/フラット列、purchase、transaction_id、value、currency、itemsの粒度|
|購買URL|完了URLパターンと再読込・戻る操作。注文IDがない場合は購入シグナル扱い|
|別購買|注文ヘッダ/明細/更新履歴、売上対象ステータス、取消・返品・税送料・値引き|
|広告費|日付×source×medium×campaign×content×term×通貨。どの粒度まで実績があるか|
|帰属|初回landingを主指標。session_inflowは重複ありの補助指標。購入直前lookbackは別モデル|
|追加要望|商品別、新規/既存会員、媒体・広告クリエイティブ、端末、再購入、CPA、LTVなど|
|出力|KPI・チャート・表・注釈、社内限定/公開、ブランド・通貨・タイムゾーン|

## 2. 調査の順序
1. `tdx-skills:tdx-basic` を読み、`tdx status` で現アカウントの文脈だけ確認する。profile/siteを切り替えない。
2. 対象DBが分かれば `tdx describe db.web --json` で列を確認する。DBが不明な場合だけDB一覧を調べる。
3. 直近の狭い時間範囲で、NULL率、空文字、会員ID・session ID有効率、GA4変数の型、注文IDと金額の反復を集計する。生の会員ID・Cookie・URLクエリをむやみに出力しない。
4. 最古/最新のログ時刻・保存期間を調べる。全期間スキャンになる場合は規模・費用を説明する。最初の履歴構築は全保持期間を対象とし、レポート期間だけでfirst-touchを作らない。
5. `queries/00_web.sql` と、必要なら `00_orders_separate.sql` / `00_costs.sql` を実際の列に合わせる。未確認のカラム名を推測して実行しない。
6. SDK session IDの欠落・再利用・有効率を確認する。欠落があるときは一部だけ混在補完せず、全体をwindow方式にするか、明示した方針で再設計する。
7. 調査結果、決定、制約、追加指標をプロジェクトの `MEMORY.md` と `config/project.json` に保存する。

## 3. 事前に確認する品質
- 会員IDは文字列で比較する。`MAX('9','10')='9'` のような文字列順序を含めて承認する。複数IDはMAXで選び、他のIDへの分配は行わない。競合件数は記録する。
- ログイン済み状態のID列だけなら「ログインイベント」ではなく「会員ID観測」と表記する。ログイン成功イベントを取れる場合はadapterの `is_login` をそれに合わせる。
- Webログの `time` が受信時刻の場合、`event_time` は実際のイベント時刻にマッピングする。パーティションは受信time、観測期限はevent_timeの両方で制御する。
- 明細の注文合計金額をSUMしない。明細金額は必要に応じてSUM、注文合計金額の繰り返しは検証後に1注文へ畳む。
- 注文履歴は取消・返品を含めた最新状態を決めてから売上対象を判定する。先に完了ステータスだけを抽出して、後の取消を落とさない。adapterでこの正本ルールを確認する。
- 注文IDのない完了URL・イベントは、注文数・購買金額・ROASに採用しない。購入シグナル数として別に出す。
- 購買データとWebの会員ID体系が違う場合は、検証済みのID変換表が必要。Cookieから人物同定できたと断言しない。
- 将来のログイン情報で、それ以前の注文を「ログイン後」に変えない。
- 広告費が媒体×月しかない場合、日×campaignに均等配分しない。集計粒度を合わせるか、承認済み配賦方法を別途実装する。
