# カート放棄・ブラウザ放棄Workflow構築Skill

顧客横展開可能なTreasure Data Digdag Workflowを構築する。ブラウザ放棄とは、商品詳細を閲覧したがカート操作・購入へ進まず離脱した状態を指す。ブラウザの終了そのものは検出せず、最後の行動からの無操作時間で判定する。

## サンプルと安全性

- 配布パスは `cart-browser-abandonment-workflow/cart-abandonment/` を使う。Skill名 `cart-abandonment-workflow` は既存環境との互換性のため維持し、3モードに対応する。
- 顧客用コピーの `config/params.yml` に設定を集約する。`params.example.yml` は初期設定の見本とする。設定変更を `-p` の上書きに依存させない。
- `cart_abandonment.dig` は共通エントリーポイントとし、`mode: cart | browser | both` で処理を選ぶ。
- 配布時はWorkflow実行・配信を無効とし、安全ガードを維持する。有効なスケジュールを付けず、設定・検証だけでメールが送られない状態を保つ。
- 顧客名・ブランド・DB・テーブル・カラム・URL・キャンペーンID・宛先を元の顧客から引き継がない。認証情報をファイルへ埋め込まない。
- `.dig` を編集する前に `workflow-skills:digdag`、TDの調査・操作前に `tdx-skills:tdx-basic`、SQL作成時に利用可能なTD SQL Skillを読み込む。Treasure WorkのTDプロファイルは変更しない。
- `tdx wf run` は必ず `--dry-run` を先に実施し、対象人数・テスト宛先・外部システム・キャンペーンを説明し、人の明示的な承認を待つ。人数がdry-runで分からなければ「不明」と伝え、読み取りで確定するまで配信実行しない。テスト送信も同じ扱いとする。

## 構築手順

### 1. 最初に施策モードをヒアリングする

他の設定より先に、次を質問する。

> 対応する施策を選んでください。①カート放棄のみ ②ブラウザ放棄のみ（商品閲覧後、カート操作・購入なし）③両方

| 回答 | `mode` | 作成対象 | ヒアリングしない不要項目 |
|---|---|---|---|
| カート放棄のみ | `cart` | カート放棄候補・送信リスト | ブラウザ用キャンペーン・閲覧商品表示仕様 |
| ブラウザ放棄のみ | `browser` | ブラウザ放棄候補・送信リスト | カート用キャンペーン・カート商品表示仕様 |
| 両方 | `both` | 両施策。共通履歴・購入除外・頻度キャップを利用 | なし |

ブラウザのみでも、**カート操作の除外シグナルは必要**。カート施策の出力テーブルや配信設定は要求しない。施策モードと、抑止に必要なイベントを混同しない。

両方では同一人物のカートを優先し、ブラウザとの同時配信を避ける方針を提案する。どの期間のカート行動でブラウザを抑止するか、端末をまたいで同一人物と扱えるかを確認する。カート配信を頻度キャップで見送ったからといって、同じ人へブラウザ配信を自動的に繰り下げない。

### 2. 選択モードに必要なデータを確認する

ソースを調査し、サンプルの共通入力スキーマへ対応付ける。DB・カラム名を推測しない。未知のものは未確認として残し、実行可能とは報告しない。

| 共通で確認するもの | 確認事項 |
|---|---|
| Webログ | DB・テーブル、時刻（Unix秒への変換）、タイムゾーン、データ遅延、イベント粒度 |
| 行動 | 商品詳細・カート操作・購入・その他の活動の識別条件、URL/パスと商品ID取得方法 |
| 識別子 | Cookie優先順位、会員ID/ハッシュメール、Cookie→人物ID対応、ログイン前後・別端末の解決方法 |
| 宛先・同意 | 人物IDとのJOIN、最新スナップショットの選び方、配信許諾・解除・抑止・スタッフ除外 |
| 購入 | 購入完了イベントと注文テーブル、注文時刻、キャンセル定義、除外期間 |
| 商品 | 商品IDとSKU/親品番の違い、商品マスタ、商品名・URL・画像、公開状態・在庫 |
| 履歴 | 過去配信・予約の定義、履歴共有範囲、メール/人物IDの正規化、保存期間 |

カート放棄を使う場合はカート内の商品構造（配列/1行1商品）、数量、削除・空カート、最新スナップショットの取り方を追加確認する。ブラウザ放棄を使う場合は商品詳細の判定と最新閲覧商品の選び方を追加確認する。`both` では両方を確認する。

匿名Cookieだけから配信可能な人物を推測しない。Cookieを複数会員で共有している場合の誤結合を避ける。安定した宛先解決がない場合はメール配信のブロッカーとする。

商品詳細イベントだけを切り出して「無操作」を判定しない。別ページ閲覧など、その後の活動も含めて最後の活動時刻を決める。

### 3. 検知・除外ルールを例で確定する

次の項目を選択モードに応じてヒアリングし、設定記録へ残す。

**共通**

- セッションの無操作時間、離脱からの待ち時間、入力遅延の余裕。セッションがまだ継続し得る時刻に送信しない。
- 対象行動の検索期間と候補の新しさ、購入の除外期間。
- 日中の実行頻度、配信禁止時間帯、夜間分のまとめ処理と境界（開始を含む/終了を含まない）。
- 施策別の上限、全施策合算の上限、日付境界とタイムゾーン。カレンダー日とローリング24時間を混同しない。
- 人物単位・メール単位の重複排除、複数サイトの履歴共有範囲。
- 最終送信リストの最大許容件数。閾値超過時は一部を勝手に送らず、停止して対象条件を確認する。

**カート放棄を使う場合**

- カート追加・カート閲覧・チェックアウト開始のどれを対象にするか。
- 最新のカートを採用するか、何商品まで表示するか。空カートや後続のカート削除をどう扱うか。
- 後続セッションの購入、別端末の購入、カート更新をどう除外するか。

**ブラウザ放棄を使う場合**

- 商品詳細URL/イベントと商品ID取得条件。対象カテゴリや除外ページがあるか。
- 最新1商品か最大N商品か、滞在最長商品も表示するか。同じ商品の反復閲覧や同時刻イベントの決定順。滞在時間を使う場合は測定方法・最低秒数・最終ページで測れない場合を決め、追加アダプターを作る。
- 同セッションだけでなく、後続セッション・別端末のカート操作や購入を人物単位で除外するか。
- 何時間前までのカート行動で抑止するか。在庫切れ・非公開・マスタ欠損商品の扱い。

例えば「10:00に商品閲覧→10:10に別端末でカート→10:20に購入→10:30にWF」「23:00の商品閲覧→翌朝まで活動なし」「同じ時刻に両施策の候補」を示し、期待する結果を確認する。結果をSQLの意味回帰テストへ落とす。

### 4. 配信経路とパーソナライズを決める

配信経路を確認する。

- **Engage Studio Always-On Campaign**：接続名、Workspace、選択施策それぞれの本番・テスト用Campaign ID、テンプレート変数、イベントIDを確認する。不要な施策のIDは要求しない。
- **外部コネクタ**：種類、接続名、送信先、認証、必須カラム、配信許諾、サンドボックス、結果の受理を確認する。利用可能なら `tdx connection schema <type>` で仕様を調べてから顧客用エクスポートを作る。サンプルを未変更のまま外部コネクタ対応済みと扱わない。

メールに表示する商品数、価格、在庫、レコメンド、ポイント、クーポンを確認する。ブラウザ用の商品項目とカート用の商品項目を明確に分ける。配信先テンプレートが既存のカラムを使う場合、無断でカラム名を変えない。商品名などの外部入力はテンプレート側でエスケープし、リンク・画像は承認済みHTTPS URLだけを使う。

サンプルの基本検知と、顧客向けの追加エンリッチメントを区別する。レコメンド・ポイント・クーポンや在庫僅少別Campaignなどは、ソース・JOIN・出力項目を顧客用コピーへ実装し、テストして初めて有効とする。参考SQLがあることだけをもって実装済みと説明しない。不要な機能のテーブルやキャンペーンは要求しない。

### 5. 顧客用Workflowを作成する

1. サンプルを新しい顧客用ディレクトリへコピーし、`tdx.json` の `workflow_project` も専用の新プロジェクト名へ変更する。配布原本・既存の本番プロジェクトは書き換えない。
2. `config/params.yml` にモード、データソース、出力DB/テーブル、時刻・除外・頻度設定を記録する。
3. 同梱READMEの入力契約に従ってソースアダプターを作り、顧客固有の複雑な変換を共通検知SQLから分離する。
4. 共通履歴と施策別送信リストを用い、`browser` では未作成のカート出力を、`cart` では未作成のブラウザ出力を参照しない。
5. `window` 設定で通常/夜間の対象期間を明示する。通常と夜間の重複・欠落、月跨ぎを検証する。同じワークテーブルへの並行実行を許さない。
6. 設定の実効値をログへ出す。切替は設定編集→検証→pushとし、`-p` を案内しない。
7. 未確定のプレースホルダー・不足する同意/購入除外があれば、実行・配信フラグを有効にしない。

初期の基本配信項目が旧サンプルや既存Campaignと異なる場合は、移行手順とカラム対応を提示する。元の高度な参考SQLを、そのまま実行可能な現行コアとして案内しない。

### 6. 静的検証と意味回帰テストを行う

- 顧客固有文字列、実宛先、UUID、接続情報、URL、クーポン、DB/テーブルの残存を調べる。参考ファイルも対象にする。
- YAML/Digdag、SQLファイル参照、変数、出力スキーマとテンプレート項目をチェックする。
- `cart` / `browser` / `both` の3モードで、不要施策のタスク・Campaign・出力参照がないことを確認する。
- 閲覧のみ、カートあり、購入あり、別端末購入、後続活動あり、識別子未解決、同意なし、解除済み、商品欠損、在庫切れをテストする。
- 境界時刻、夜間分、同日再実行、両施策の競合、施策別/合算キャップをテストする。
- ローカルの模擬実行と実TDでのSQL検証を区別する。ローカルテストに通っても、実TD・接続先での実行成功と報告しない。
- CLIの `tdx wf --help` で対応コマンドを確認する。`validate` が利用できる版ではそれを優先し、非対応の版で検証済みと報告しない。実行前には必ず `tdx wf run <workflow> --dry-run` を行い、外部送信の承認前に本実行しない。

### 7. テスト送信・本番切替を承認付きで進める

1. `send_email_test.dig` の単一エントリーポイントを使う。切替が必要なら設定ファイルのテストモードを使う。
2. 元の宛先をテスト宛先へ置き換える。正確な宛先、各施策のCampaign、バリエーション数と想定メッセージ数を提示する。
3. 同意済みのテスト宛先・本番から分離したCampaign・許可された商品データを使う。本番宛先へフォールバックしない。
4. dry-run結果を説明し、明示的な承認後にだけ実行する。テスト履歴を本番頻度キャップへ混入させない。
5. 本番切替は別の承認を得る。重複実行・再試行で二重配信し得る箇所と、履歴が予約・送信要求・配信成功のどれを意味するかを説明する。コネクタの受理は受信トレイ到達ではない。
6. 配信スケジュールは最後に、顧客が承認した時刻だけ有効にする。

## ヒアリング記録

以下は意思決定の記録であり、実行用configと混同しない。実行用のキーは同梱の `config/params.example.yml` に合わせる。

```yaml
mode: "<cart | browser | both>"
inputs:
  events: "<DB.TABLEと変換方法>"
  identities: "<Cookieから人物IDへの解決規則>"
  recipients: "<最新の宛先・同意・抑止>"
  orders: "<購入イベントと注文除外>"
logic:
  cart_rule: "<選択時のみ。ブラウザ抑止用のカートシグナルは別途必須>"
  browser_rule: "<選択時のみ。PDPと商品ID>"
  session_timeout_seconds: "<確認値>"
  wait_minutes: "<確認値>"
  input_delay_minutes: "<確認値>"
  cart_suppression_window: "<確認値>"
  purchase_exclusion_window: "<確認値>"
  frequency_caps: "<施策別・合算・日付境界>"
  overlap_policy: "<cart優先など>"
delivery:
  route: "<engage_studio | external_connector>"
  campaigns: "<選択した施策分だけ>"
testing:
  recipients: []
  expected_messages: "<確認値>"
unresolved: []
```

## 出力形式

1. **確定した設定** — 選択モード、定義・除外、データソース、配信経路、表示項目、頻度・夜間設定。
2. **成果物** — 顧客用コピー、config、ソースアダプター、SQL、Workflow、テスト。
3. **未確認事項** — プレースホルダー、Campaign・入力・追加機能のブロッカー。
4. **検証状況** — ローカル検証、TDでの検証、dry-runを分けて報告。
5. **送信安全性** — 未送信/承認待ち/承認済み実行とその対象。GitHub公開とTDへの反映も区別する。

## 対応例

- 「ブラウザ放棄だけ、最新閲覧1商品」→ `mode: browser`。PDP・商品ID・宛先解決、人物単位のカート/購入抑止を確認する。カート用Campaignは聞かない。
- 「カート放棄だけ、商品4件とレコメンド」→ `mode: cart`。最新カートの粒度を確認し、レコメンドアダプターとテンプレート項目を実装・テストする。ブラウザ用Campaignは聞かない。
- 「両方」→ `mode: both`。カート優先・共有頻度キャップを提案し、同一人物が両方の候補になるテストを必ず行う。
- リアルタイムログ・宛先解決・購入シグナルがない→制約を説明する。検知の遅延や誤配信を隠して本番化しない。
