# 共有作業フォルダと MEMORY.md の運用ルール

CRM PDCA は、段階を追って複数日にわたり、担当者をまたいで進みます。
そのため **生成物はチーム全員が開ける場所に置き**、**誰がいつ何を進めたかを MEMORY.md に時系列で残す** ことを全Skill共通のルールとします。

---

## 1. 保存先は「my」以外の共有作業フォルダ

### なぜ必要か
Treasure AI Studio では、仕様として本人しかアクセスできない **`my` フォルダ** が作成されます。
ここに Skill・設定・成果物を置くと、他のメンバーが開けず、引き継ぎもレビューもできなくなります。

### ルール
1. **共有作業フォルダ** ＝ `.claude/skills/`、`projects/`、`MEMORY.md` を置くフォルダ。
2. 共有作業フォルダは、**`my` という名前のフォルダそのもの、またはその配下であってはならない。**
   判定方法: 絶対パスを `/` で区切ったとき、`my` と一致する要素（大文字小文字を区別しない）が1つでもあれば NG。
   - NG: `/…/my`、`/…/my/crm`、`/…/my/projects/…`
   - OK: `/…/crm-pdca`、`/…/shared/crm-pdca`（`mypage` や `my-team` のように `my` と完全一致しない名前は対象外）
3. 現在のフォルダが NG のときは、**`my` と同じ階層（`my` の親フォルダ）に新しいフォルダを作成** して共有作業フォルダにする。
   - フォルダ名は候補を2〜3個示して利用者に選んでもらう（例: `crm-pdca`、`<ブランド名>-crm-pdca`）。
   - 作成したら、そのフォルダが他のメンバーからも見えるかを利用者に確認してもらう。
4. 共有作業フォルダの絶対パスは `config/environment.yml` の `workspace.root` に記録する。
   以降、`projects/`・`MEMORY.md` などのパスは **カレントディレクトリではなく `workspace.root` を基準に解決** する。
5. **ファイルを書き込む直前に毎回** 保存先の絶対パスを 2. の方法で確認する。NG なら書き込まずに止め、共有作業フォルダを確認する。
   対象: `project_state.json`、`01_plan/`〜`04_action/` の成果物、クエリ、スナップショット、HTMLレポート、`_index.md`、`learnings.md`、`MEMORY.md`、`config/` 配下のすべて。
6. 利用者が明示的に「`my` に保存して」と頼んだ場合も、他のメンバーに共有できなくなることを伝え、共有作業フォルダへの保存を提案する。それでも希望された一時ファイル（下書き等）は保存してよいが、**PDCAの正式な成果物・設定・MEMORY.md は必ず共有作業フォルダに置く。**

### 既存インストールが my 配下にあった場合
1. 共有作業フォルダを新しく作成する（上記 3.）。
2. `.claude/skills/crm-*`、`projects/`、`MEMORY.md`（あれば）を **コピー** する（移動ではなくコピー）。
3. `workspace.root` を新しいパスに更新し、MEMORY.md に `migration` として記録する。
4. 元の `my` 配下のファイルの削除は利用者の判断に任せ、AIは削除しない。

## 2. MEMORY.md — 時系列の作業記録

### 置き場所と役割
- 場所: `<workspace.root>/MEMORY.md`（共有作業フォルダの直下。`my` には置かない）
- 役割: **ワークスペース全体の作業履歴**。セットアップ・設定変更・全プロジェクトの進捗・承認・引き継ぎを1つのファイルで時系列に追える。
- `project_state.json` との違い:

| ファイル | 単位 | 読み手 | 内容 |
|---|---|---|---|
| `MEMORY.md` | ワークスペース全体 | 人とAI | いつ・誰が・何をしたか、次に何をするか（時系列） |
| `projects/<id>/project_state.json` | プロジェクト単位 | 主にAI | 現在のフェーズ・承認状態・成果物パス（最新状態） |

### 構成
MEMORY.md は2つのセクションで構成する（テンプレート: `setup/MEMORY.template.md`）。

1. **現在の状況** — 最新状態の要約。記録のたびに **上書き更新** する（10行程度）。
   - 共有作業フォルダのパス / 設定の最終更新日
   - 進行中プロジェクトとフェーズ
   - 承認待ち・未確認事項
   - 次にやること（誰が・何を）
2. **更新履歴** — **追記のみ**。古いものが上、新しいものが下。
   - 過去のエントリは編集・削除しない。誤りは新しいエントリで「訂正」として記録する。

### エントリの書式

```markdown
### YYYY-MM-DD HH:MM (<タイムゾーン>) — <種別> — <対象>
- 担当者: <名前または役割>（AI実行の場合は「<名前> + AI(【PM】等)」）
- 内容: <何をしたか。1〜3行>
- 決定・承認: <承認ポイント・選択肢・判断理由。無ければ「なし」>
- 変更ファイル: <workspace.root からの相対パス（複数可）>
- 次の作業: <次に誰が何をするか。引き継ぎ事項>
```

- 日時は `organization.timezone`（未設定なら `Asia/Tokyo`）で書く。
- **担当者名** はセッション開始時に確認する（後述）。メールアドレスなどの個人情報は書かない。
- `<対象>` は `setup`、`config`、`<project-id>`、`workspace` のいずれか。

### 種別

| 種別 | 記録するタイミング |
|---|---|
| `setup` | 初回セットアップ完了時 |
| `config-change` | `environment.yml` / `data-sources.md` の変更、`<TO_BE_CONFIRMED>` の確定 |
| `migration` | 共有作業フォルダの作成・移行 |
| `skill-update` | Skill本体の更新（再セットアップ・差分更新） |
| `project-created` | プロジェクト立ち上げ |
| `phase-start` | フェーズ開始（担当者が変わったときは特に） |
| `approval` | 承認①〜④の結果（承認・修正・中止のいずれも） |
| `tdx-run` | 書き込みを伴う tdx 操作（セグメント作成・テンプレート更新・Workflow push など） |
| `delivery` | 配信の実行・予約・停止 |
| `phase-complete` | フェーズ終了と次フェーズへの引き継ぎ |
| `handover` | 作業を途中で止めるとき・担当者を交代するとき |
| `learning` | `learnings.md` への追記 |
| `archive` | プロジェクトの完了・アーカイブ |
| `correction` | 過去エントリの訂正 |

読み取り専用のクエリや軽微な表記修正は記録しなくてよい。迷ったら記録する。

## 3. 全Skill共通の手順

### 開始時（/crm-pdca、/crm-plan、/crm-do、/crm-check、/crm-action、セットアップ）
1. `config/environment.yml` の `workspace.root` を読み、共有作業フォルダが `my` 配下でないことを確認する。
   - `workspace` の項目が無い（旧バージョンでセットアップした）場合は、`.claude/` の親フォルダを共有作業フォルダとみなし、`my` 判定を行ったうえで `workspace.root` を追記する（`config-change` として記録）。
2. `<workspace.root>/MEMORY.md` を読む。
   - 「現在の状況」と、更新履歴の **直近10件程度** を確認し、利用者に2〜4行で伝える。
     例: 「前回は 10/14 に佐藤さんが dormant-revive-2026Q4 の承認②（KPI）まで完了しています。次は【施策】のセグメント設計です。」
   - MEMORY.md が無い場合は `setup/MEMORY.template.md` の形式で作成し、`migration` または `setup` として最初のエントリを書く。
3. **担当者名を確認する。** 「今回の作業担当者のお名前（または役割）を教えてください」と1回だけ聞く。同じセッション内では聞き直さない。

### 作業中
- 上の「種別」に当たる出来事が起きたら、その場で MEMORY.md に追記し、「現在の状況」を更新する。
- 承認①〜④は、`project_state.json` の `approvals` と `history` を更新したうえで、MEMORY.md にも `approval` として記録する。
- `project_state.json` の `history` にも `by`（担当者名）を入れる。

### 終了時・中断時
- 作業を終えるとき、または利用者が離席・交代する場合は `handover` を記録する。
  - どこまで終わったか / 未完了の作業 / 次の担当者が最初にやること / 承認待ちの項目
- 次の担当者は MEMORY.md を読むだけで続きから始められる状態にする。

## 4. 書き込みのチェックリスト

ファイルを書き込む前に確認する:

- [ ] 保存先の絶対パスに `my` と一致する要素がない
- [ ] 保存先が `workspace.root` 配下である
- [ ] MEMORY.md に記録すべき出来事なら、追記と「現在の状況」の更新を行った
- [ ] 秘密情報（APIキー・パスワード・メールアドレス）を書いていない
