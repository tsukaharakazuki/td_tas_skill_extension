# プロジェクト管理の在り方（CRM施策PDCA）

## 1. 基本思想

CRM施策は「1本の施策」ではなく「学び続けるサイクル」。
プロジェクト管理は、以下を同時に満たす必要がある。

- 🔎 **トレーサビリティ**: いつ・誰が・何を決めたか辿れる
- 🔁 **再利用性**: 過去プロジェクトの学びを次に活かせる
- ⚡ **軽量さ**: 管理のための管理にならない
- 👥 **協業性**: AI 4ペルソナ × クライアント が同じ情報を見られる

## 3. プロジェクトの立ち上げ方

### 3-1. プロジェクトタイプ（典型例）

| タイプ | project-id 例 | 目的 |
|---|---|---|
| 休眠掘り起こし | `dormant-revive-2026Q4` | 離反顧客の再アクティブ化 |
| 新作キャンペーン | `spring-new-2026`, `fw2026-launch` | 新商品の告知・初動形成 |
| F2転換 | `f2-conv-2026-10` | 初回購入→2回目購入促進 |
| クロスセル | `cross-sell-brandX-2026` | 既存顧客への別ブランド提案 |
| LTV向上 | `ltv-up-vip-2026H2` | 高LTV層のさらなる引き上げ |
| 離反予防 | `churn-prev-2026Q4` | 離反兆候顧客の引き留め |
| 季節イベント | `xmas-2026`, `motherday-2026` | 季節需要の取り込み |

### 3-2. project-id 命名規則
`<目的スラッグ>-<年Q or 日付>`

- スラッグは英小文字+ハイフン
- 年: 2026, 2026Q4, 2026-10 など
- 短く、人間が読んで意味が分かる

### 3-3. プロジェクト立ち上げフロー
PM が実行:

1. **AskUserQuestion**: プロジェクトタイプを選定
2. **AskUserQuestion**: project-id 候補を2〜3個提示 → ユーザーが選択
3. **Bash**: `mkdir -p projects/<project-id>/{01_plan,02_do,03_check,04_action}`
4. **Write**: `project_state.json` を `templates/` からコピー＆初期化
5. **Write**: `projects/<project-id>/README.md` を作成（施策概要）
6. **Edit**: `projects/_index.md` に新プロジェクトを追記

## 4. project_state.json — 単一の真実の源 (SSoT)

### 設計原則
- **軽量な JSON** で、全フェーズの進捗・承認・成果物パスを一元管理
- 詳細は Markdown 成果物に。JSON はインデックスとステータスのみ
- PMが各フェーズ節目に更新する

### フィールド概要（`templates/project_state.json` 参照）
- `status`: active / paused / completed / archived
- `current_phase`: plan / do / check / action
- `cycle`: 現在のサイクル番号（1, 2, 3...）
- `pm_scope`: 4ペルソナの自動化レベル
- `approvals`: 4つの承認ポイントの状態
- `artifacts`: 各成果物の相対パス
- `history`: イベントログ

### 更新タイミング
- フェーズ移行時
- 承認取得時
- KPI確定/判定時
- 中止/完了時

## 6. マルチプロジェクトの並行運用

### 原則
- 同時進行は **3プロジェクトまで** を推奨（AI/人間の集中力確保）
- 配信ウィンドウが重なる場合は **顧客重複** を要確認
  - 同じユーザーが複数施策から1週間に3通超受信しないか
- クリエイティブ・コピーのトーンが衝突しないか

### 顧客重複チェック（Plan承認③前に必須）
```sql
-- 進行中他プロジェクトのセグメントと重複する顧客数を確認
-- customer_id は environment.yml の id_mapping に従って基準IDへ揃える
SELECT COUNT(DISTINCT customer_id) AS overlap
FROM <this_segment>
WHERE customer_id IN (SELECT customer_id FROM <other_active_segment>);
```

配信上限は `defaults.frequency_cap` を基準にする。

## 7. 学びの蓄積と横展開

### learnings.md
全プロジェクト横断で得られた知見のストック。
PMがプロジェクト完了時に追記。

```markdown
# CRM施策 学びログ

## カテゴリ: 休眠掘り起こし
- 180日以上の休眠層にはクーポン訴求より「お久しぶり」感情訴求が刺さる（dormant-revive-2026Q4, 2026-10）
- 配信時刻は火曜10:00 or 金曜19:00 が開封率◎

## カテゴリ: F2転換
- 初回購入30日以内のアプローチが最大効果（f2-conv-2026-10, 2026-10）
- クーポンよりコーディネート提案の方がCVR高い（brand<X>に限る）

## カテゴリ: チャネル
- LINE CTR は メール の 2.3倍 (平均)
- SMS は到達率◎だが情報量不足、他チャネルとのコンボ推奨
```

### 横展開の判断フロー
Action承認④で「D: プロジェクト完了」が選ばれたとき、PMが以下を提案:
1. 本プロジェクトの学びを `learnings.md` に転記
2. 類似シチュエーションのプロジェクト候補を2〜3件提示
3. 新プロジェクト立ち上げの打診

## 8. アーカイブ・リバイバル

### アーカイブ条件
- プロジェクト完了（Action D）後 30日経過
- または 中止後 7日経過

### アーカイブ処理
```bash
mv projects/<project-id> projects/_archive/
```
`_index.md` のアーカイブセクションに移動。`project_state.json` は保持（将来の分析用）。

### リバイバル
類似施策を再度始めるとき、アーカイブから `README.md` と `04_action/next_action.md` を参照して新プロジェクトを立ち上げる。

## 9. ペルソナ業務範囲（pm_scope）の運用

プロジェクトごとにクライアントが決める3段階:

| レベル | 意味 | 例 |
|---|---|---|
| `full_auto` | AI が自律的に判断・実行 | 定型化された週次PDCAの分析担当 |
| `consult` | AI が提案し、人間が決める | 新規施策の施策担当・CR担当 |
| `human_led` | 人間が主、AI は補助 | 初めての施策タイプの PM 判断 |

Plan 開始時の `pm_scope` を `project_state.json` に記録し、途中変更時は `history` に追記。

## 10. 失敗パターンと回避

### A. 承認を取らずに進めてしまう
→ 本Skillは4つの承認ポイントを**スキップ不可**として設計。各フェーズファイルに🙋マーク。

### B. 分析のための分析が終わらない
→ Plan ステップ3の分析は **1日以内** を目安に。深掘りはCheckで。

### C. 配信が複数プロジェクトで衝突
→ 承認③前の顧客重複チェックを必須化。

### D. Check の判定が主観的
→ Plan ステップ5で**定量KPI**を必ず確定（承認②）。Check判定は数値ベースで。

### E. 学びが活用されない
→ プロジェクト完了時の learnings.md 追記を必須ステップに。
