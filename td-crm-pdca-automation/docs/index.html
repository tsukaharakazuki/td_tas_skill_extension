Treasure AI - CRM施策PDCA Skill 活用ガイド

休眠掘り起こし、新作告知、F2転換などのCRM施策を、4つのAIペルソナが分担して Plan → Do → Check → Action まで回します。人は要所の意思決定に集中し、学びはプロジェクトをまたいで蓄積されます。

1サイクルの流れ

Plan→承認①②③→Do→Check→Action→承認④

分析・設計・レポートはAIが担当し、方向性・KPI・配信内容・次の一手は人が決めます。tdx の実行や配信の前にも、必ず確認が入ります。

このSkillでできること

CRM担当者1人でも、PM・アナリスト・施策担当・クリエイティブのチームで進めるような段取りで施策を回せます。

4AIペルソナ（PM・分析・施策・CR）
4スキップできない人の承認ポイント
7対応する施策タイプ
10〜15分対話形式の初期セットアップ

特定企業のテーブル定義は持っていません。最初に環境をヒアリングし、その会社専用の設定と分析SQLを生成してから使います。

設定の中心： .claude/skills/crm-pdca/config/environment.yml にテーブル・ID対応・売上ルール・Parent Segment・チャネルを集約。reference/data-sources.md には、実際のテーブル名・カラム名に置き換えた、そのまま実行できる定番SQLが入ります。分からない項目は <TO_BE_CONFIRMED> として残り、必要になった時点でAIが改めて確認します。

4つのAIペルソナ

発言の冒頭にペルソナ名が付くので、誰の立場の提案かが一目で分かります。任せる範囲は、プロジェクトごとにペルソナ単位で決めます。

【PM】

プロジェクトマネージャー

施策全体の進行役。目的・制約をヒアリングし、各担当に指示書を出し、承認の場を回します。

  • 施策ブリーフの作成
  • 承認ポイントの進行
  • 進捗・意思決定の記録
  • 学びの横展開の提案
【分析】

分析担当

「数字で語る」担当。事前分析で対象の規模と特徴を示し、配信後はKPIの達成度を判定します。

  • セグメント候補の人数試算
  • KPIの現状値の算出
  • 配信・流入・行動・購買の分析
  • コントロール群との比較
【施策】

施策担当

方向性を実行できる配信プランに落とし込みます。チャネル選定・セグメント定義・配信実務を担当します。

  • チャネルとスケジュールの設計
  • セグメント条件の定義
  • 配信上限と重複のチェック
  • CJOジャーニーの設計
【CR】

クリエイティブ企画

方向性を「読まれる・響く・動かす」表現に変えます。訴求軸・コピー・A/Bテストを設計します。

  • 件名・本文・CTAの案出し
  • A/Bテストの設計（1変数ずつ）
  • 法務・配信前のチェック
  • 開封率・CTRの読み解き

任せる範囲の3段階

  • full_auto：AIが自律的に判断・実行（定型化した週次分析など）
  • consult：AIが提案し、人が決める（新しい施策の標準）
  • human_led：人が主導し、AIは補助（初めての施策タイプなど）

どの範囲でも変わらないルール

  • 4つの承認ポイントは、full_autoでもスキップしない
  • tdx を実行する前に、コマンドと目的を示して承認を取る
  • 配信（外部への送信）は、件数・チャネル・日時を確認してから実行
  • 設定にないテーブル・カラムは推測せず、確認してから使う

PDCAの4フェーズ

各フェーズの成果物は projects/<project-id>/ に保存され、進捗は project_state.json で一元管理します。フェーズ単位での起動もできます。

PHASE 1 · /crm-planPlan — 施策を設計する

目的のヒアリングから、分析・方向性・KPI・セグメント・クリエイティブまでを決め、配信できる状態にします。

進め方
  1. 【PM】目的・ターゲット仮説・期待成果・制約をヒアリング
  2. 【PM】→【分析】分析の指示書を発行
  3. 【分析】対象の規模・特徴・KPIの現状値を分析
  4. 承認① 施策の方向性
  5. 承認② KPIと目標値
  6. 【施策】セグメント・チャネル設計 ／【CR】訴求軸・コピー（並行）
  7. 承認③ セグメント＆クリエイティブ最終確認
  8. セグメント作成、配信ツールでコンテンツを仕上げる
成果物：brief.md / analysis.md / direction.md / kpi.md / segment_spec.md / creative_spec.md
ヒアリング承認3回

PHASE 2 · /crm-doDo — 配信する

配信直前の最終チェックをすべてクリアしてから実行し、何をいつ誰に送ったかを記録します。

配信直前チェック

セグメント件数・除外対象・配信許諾・配信上限・リンク切れ・差し込みのダミー値・コントロール群・配信時間帯・法務チェック

問題があったら？

PMがすぐに人へエスカレーションし、配信を止めるか、修正して再承認を取ります。

成果物：delivery_log.md（日時・チャネル・セグメント・配信数・ジョブID）と配信直後のスナップショット
外部送信は要承認配信ログ

PHASE 3 · /crm-checkCheck — 効果を測る

配信から一定期間（既定3日）待ってから、5つの観点で多角的に分析し、KPIと数値で突き合わせます。

分析の観点

A 配信（到達・開封・CTR・エラー） B Web流入 C サイト内行動 D 購買（CV・CVR・売上・LTV増分） E セグメント別・コントロール群比較

判定基準（変更可）

達成率 ◎110%以上 / ○90〜110% / △70〜90% / ✗70%未満

成果物：analysis_report.md / insights.md（主要発見3つ・想定外の発見・次サイクルの仮説）
数値で判定振り返り会議

PHASE 4 · /crm-actionAction — 次の一手を決める

PMが総括し、施策担当とCRが修正案・継続案を出して、次のサイクルを人が決めます。

選択肢

A 現状継続（対象拡大） B 修正して継続 C 中止・ピボット D プロジェクト完了（学びを横展開）

その後

継続・修正ならサイクル番号を増やしてPlanへ戻ります。完了なら学びを projects/learnings.md に追記し、横展開できるプロジェクトを提案します。

成果物：next_action.md（決定内容・判断理由・承認日時）
承認④学びの蓄積

人が決める4つのポイント

AIが先に進めすぎないよう、ここだけは必ず止まって確認を取ります。選択肢と推奨案がセットで提示されます。

APPROVAL 01 · PLAN

施策の方向性

分析結果をもとに、ターゲットと訴求軸の案（A/B）からどれで進めるかを決めます。

APPROVAL 02 · PLAN

KPIと目標値

Checkで良し悪しを判定する主KPI・副KPIと目標値を、配信前に確定させます。

APPROVAL 03 · PLAN

セグメント＆クリエイティブ

セグメント作成・配信ツールへ投入する直前の最終確認です。承認・修正・中止から選びます。

APPROVAL 04 · ACTION

次サイクルの意思決定

Checkの結果を受けて、継続・修正・中止・完了のどれにするかを決めます。

なぜKPIを配信前に決めるのか： 配信後に指標を選ぶと、良かった数字だけを拾ってしまいがちです。承認②で判定基準を先に固めておくことで、Checkの判定が主観に流れません。

セットアップで確認すること

Treasure Dataにあるデータの場所と、自社の売上ルールを確認します。分からない項目は「後で」と答えれば先に進めます。

テーマ確認する内容使われる場面
A組織・基本設定会社・ブランド名、複数ブランドの区別、タイムゾーン、通貨と税込/税抜レポートの見出し、期間の集計
B顧客（会員）マスタ顧客ID、チャネル別の配信許諾、属性、集計済みのRFM・LTV、除外すべき顧客セグメント条件、休眠・LTV分析
C購買データと売上ルール1行の単位、注文ID、金額の重複、キャンセル・返品の判定、商品・ブランド・カテゴリ売上・CVR・F2転換の計算
DWebアクセスログセッションID、ページ判定（商品詳細・カート・購入完了）、配信経由流入の判定（UTMなど）CheckのWeb流入・サイト内行動
EID対応Web・購買・会員・配信のIDを、どう基準IDにそろえるかテーブルをまたぐ分析すべて
Fセグメント・配信基盤Parent Segment、チャネル、Engage Studio・CJO・外部ツール、配信結果の集計テーブル、コントロール群Plan・Doでのセグメント作成と配信
G運用ルール社内の連携Skill、ペルソナの既定範囲、配信上限、避ける時間帯、法務チェック、判定基準配信前チェック、KPI判定
データがそろっていなくても始められます： Webログがない環境では、CheckのWeb流入・サイト内行動を省略して進めます。顧客マスタに集計済みのRFM指標がなければ、購買データから算出するSQLが生成されます。

施策タイプ別の進め方

プロジェクトIDは <目的>-<時期> 形式で命名します。同時に進めるのは3プロジェクトまでが目安です。

休眠掘り起こし

dormant-revive-2026Q4 · 離反顧客の再アクティブ化
Planの分析最終購入からの経過日数別の人数・平均購入回数
セグメント例最終購入から90〜365日、購入1回以上、配信許諾あり
Checkの要点コントロール群との購買率の差、休眠期間帯ごとの反応差

新作キャンペーン

spring-new-2026 · 新商品の告知と初動づくり
Planの分析ブランド・カテゴリ別の購買者数、関連カテゴリの購買傾向
セグメント例同ブランド・同カテゴリの購買経験者、直近の閲覧者
Checkの要点配信経由の流入と商品ページ到達率、初週の売上

F2転換

f2-conv-2026-10 · 初回購入から2回目購入へ
Planの分析初回購入者のF2転換率と、転換までの日数
セグメント例購入1回、初回購入から30〜60日経過
Checkの要点配信後14日の2回目購入率、クーポン有無での差

クロスセル

cross-sell-brandX-2026 · 別ブランド・別カテゴリの提案
Planの分析ブランド間の併買傾向、購買経験ブランドの分布
セグメント例ブランドXのみ購入、ブランドYの閲覧あり
Checkの要点他ブランドの購入率、客単価の変化

LTV向上・VIP施策

ltv-up-vip-2026H2 · 優良顧客のさらなる引き上げ
Planの分析LTV上位層の購買頻度・単価・好みのカテゴリ
セグメント例LTV上位10%、最終購入30日以内
Checkの要点配信後30日のLTV増分（コントロール群との差）

離反予防・季節イベント

churn-prev-2026Q4 / xmas-2026 · 引き留めと季節需要
Planの分析購入間隔が延びている顧客、過去の同時期の売れ筋
セグメント例平均購入間隔を超えた顧客、昨年同時期の購入者
Checkの要点離反率の変化、イベント期間の売上

推奨導入ステップ

最初から全部を任せず、1施策を人と一緒に回して、設定と判定基準を固めてから範囲を広げます。

1

セットアップ

テーブル・ID対応・売上ルールを確認。定番SQLが実データで動くことを確かめます。

2

1施策を consult で

休眠掘り起こしなど効果の見えやすい施策を、全ペルソナ consult で1サイクル回します。

3

計測基盤を整える

配信結果の集計テーブルとコントロール群の運用を整え、Checkを数値で判定できるようにします。

4

並行運用・横展開

定型化した分析は full_auto に。学びログを使って、複数施策を並行で回します。

設定を変えたいとき： 同じURLを読み込んで「CRM PDCAの設定を変更したい」と依頼すると、変更したいテーマだけを聞き直します。projects/ の既存プロジェクトと学びログは上書きされません。
